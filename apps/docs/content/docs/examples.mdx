RGAP treats MCP servers and their exposed operations as resources. A
deployment registers each trusted server beneath an administrative resource
and assigns stable IDs to servers, tools, prompts, and MCP resources.

## Invoke OpenAI through a resource

Provider credentials stay in deployment configuration. The model name is
sealed executable input, so each resource fixes the model its runtime calls.
The runtime returns only generated text:

```ts
import { createOpenAI } from '@ai-sdk/openai';
import { generateText } from 'ai';

const OpenAIInputSchema = z.object({
  model: z.string(),
  prompt: z.string().min(1),
});

const openai = createOpenAI();
const openaiRuntime: InvokeRuntime<OpenAIInput, OpenAIOutput> = {
  inputSchema: OpenAIInputSchema,
  outputSchema: OpenAIOutputSchema,
  async invoke({ input, signal }) {
    const { text } = await generateText({
      model: openai(input.model),
      prompt: input.prompt,
      abortSignal: signal,
    });
    return { text };
  },
};
```

Creating the executable resource accepts its runtime and sealed literal input
in the same atomic command:

```ts
const model = await admin.resources.create({
  name: 'openai/gpt-5.6-sol',
  executable: {
    runtime: 'openai',
    input: {
      model: 'gpt-5.6-sol',
    },
  },
});

const employeeGrant = await admin.grants.create({
  name: 'company/platform-team/employee',
  resources: [{ id: model.id, permissions: ['invoke'] }],
  expiresAt: null,
});
const employeeToken = await employeeGrant.tokens.create({ label: 'employee' });
const employee = store.as(employeeToken.value);
const authorizedModel = await employee.resources.get(model.id);

for await (const event of authorizedModel.invoke({
  input: { prompt: 'Summarize why capability attenuation matters.' },
})) {
  console.log(event);
}
```

The employee receives only `invoke` on the executable model resource. Callers
cannot replace its sealed model name. The complete executable version lives in
`examples/openai.ts`.

## Compose a secret-backed resource

A deployment stores each credential under an ordinary RGAP resource ID. An
administrator seals that resource into a trusted executable and exposes only
the executable's narrow interface:

```ts
const githubToken = await admin.resources.create({
  name: 'users/alice/secrets/github-token',
});
await secretStore.set(githubToken.id, process.env.ALICE_GITHUB_TOKEN);

const githubProfile = await admin.resources.create({
  name: 'users/alice/functions/github-profile',
  executable: {
    runtime: 'githubProfile',
    bind: { credential: githubToken.id },
  },
});
```

The `bind` map partially applies top-level input fields with ordinary resource
ID strings. Setting a binding requires `bind` on its resource and records the
authorizing grant lineage. Invocation revalidates that lineage and rejects
caller input that attempts to replace a sealed field.

The trusted runtime reads the credential from the deployment-owned store and
returns only the operation result:

```ts
const githubProfileRuntime = {
  inputSchema: z.object({ credential: z.string() }),
  outputSchema: z.object({ login: z.string() }),
  async invoke({ input }) {
    const token = await secretStore.get(input.credential);
    if (token === undefined) throw new Error('Credential is unavailable.');
    return fetchGithubProfile(token);
  },
} satisfies InvokeRuntime<{ credential: string }, { login: string }>;
```

The administrator gives Alice authority to compose the safe function and to
invoke resources under her scripts subtree, but gives her no authority over
the credential:

```ts
const scripts = await admin.resources.create({ name: 'users/alice/scripts' });
const author = await admin.grants.create({
  name: 'users/alice/script-author',
  resources: [
    { id: scripts.id, permissions: ['write', 'invoke'] },
    { id: githubProfile.id, permissions: ['bind'] },
  ],
  expiresAt: null,
});
const authorToken = await author.tokens.create({ label: 'script-author' });
```

Alice creates another executable resource and binds the safe function as its
direct dependency:

```ts
const alice = store.as(authorToken.value);
const script = await (await alice.resources.get(scripts.id)).create({
  name: 'profile-summary',
  executable: {
    runtime: 'profileSummary',
    bind: { profile: githubProfile.id },
  },
});

const actingAuthor = await alice.grants.get(author.id);
const consumer = await actingAuthor.create({
  name: 'profile-consumer',
  resources: [{ id: script.id, permissions: ['invoke'] }],
  expiresAt: null,
});
const consumerToken = await consumer.tokens.create({ label: 'consumer' });
```

The composition runtime invokes that named binding. It receives the profile
result and never receives the transitive credential binding:

```ts
const profileSummaryRuntime = {
  inputSchema: z.object({ profile: z.string() }),
  outputSchema: z.string(),
  async invoke({ input, invoke }) {
    const profile = await invoke.one<{ login: string }>(
      input.profile,
      { input: {} },
    );
    return `GitHub user: ${profile.login}`;
  },
} satisfies InvokeRuntime<{ profile: string }, string>;
```

Creating the `profile` edge requires `bind` on `githubProfile`. When the script
runs, RGAP revalidates that edge and invokes the arbitrary resource ID in
`input.profile`. The profile's frame then revalidates its own credential edge.
This transitive call chain never grants the script's frame direct authority to
bind or read `githubToken`.

The consumer can invoke `script` without receiving `bind` on `githubProfile`.
This is the intended meaning of `bind`: Alice can encapsulate the safe profile
capability and publish her wrapper's interface. Revoking or narrowing
`author` invalidates the recorded `profile` edge on its next invocation and
therefore disables it for every consumer.

The complete Hono app lives in `examples/secret-store`. It uses one SQLite
database for RGAP state and initializes `SqliteSecretStore` with another
SQLite database for secret values. Inputs, outputs, and secret values stay out
of invocation audit records, logs, and errors.

## Proxy a remote MCP server

`examples/mcp-proxy` is a Hono app that acts as an OAuth-compatible MCP
client. RGAP holds the server as a resource. Invocation sends MCP JSON-RPC to
that sealed origin. OAuth access tokens never enter RGAP state.

The app registers one trusted `mcpClient` runtime and three executables that
share a credential binding and a sealed server URL:

```text
mcp/demo/
├── credential     # secret-store key for DCR client + tokens
├── authorize      # operation=authorize, seals callback resource ID
├── callback       # operation=callback
└── rpc            # operation=rpc
```

The server URL is sealed input. The credential resource is a `bind` edge. A
caller supplies only the MCP method and params, or the OAuth `code` and
`state` on callback. That is the confused-deputy rule from privilege
delegation: the runtime attaches the stored token only to the sealed origin.

```ts
const rpc = await admin.resources.create({
  name: 'mcp/demo/rpc',
  executable: {
    runtime: 'mcpClient',
    input: { serverUrl, operation: 'rpc' },
    bind: { credential: credential.id },
  },
});
```

Invoking `rpc` with `{ method: 'tools/call', params: { name: 'echo',
arguments: { text: 'hello' } } }` is an MCP JSON-RPC call to that server.
Granting `invoke` on this resource is the server-level governance boundary.
Tool leaves under the same server come later: each tool resource seals
`operation`, `serverUrl`, and the tool name so a caller supplies only
arguments.

### OAuth through invoke

MCP HTTP servers advertise an authorization server with protected-resource
metadata. The proxy runtime discovers that metadata, registers with dynamic
client registration when needed, and starts authorization-code plus PKCE:

<Steps>
  <Step>
    ### Invoke authorize

    The consumer invokes the authorize resource. The runtime stores a PKCE
    verifier and OAuth `state` in the secret store, then returns an
    `authorizationUrl`.
  </Step>
  <Step>
    ### Redirect to the public callback

    The authorization server redirects the browser to `GET /oauth/callback`.
    RGAP invoke is POST with a bearer, so this route is a sibling of the RGAP
    API rather than a `createApp` route. `createApp` requires a bearer on
    every path except OpenAPI.
  </Step>
  <Step>
    ### Invoke callback

    The HTTP adapter looks up `state`, then invokes the callback resource with
    `{ code, state }` using a deployment grant that can invoke only that
    resource. The callback runtime verifies the session against its sealed
    server URL and bound credential, exchanges the code, and stores tokens.
  </Step>
  <Step>
    ### Invoke RPC

    Later `rpc` invocations refresh the access token when needed, initialize
    an MCP session, and forward JSON-RPC. A missing token fails with an
    authorization error rather than returning a login URL.
  </Step>
</Steps>

The consumer grant contains `invoke` on authorize and rpc only. It has no
permission on `credential` or `callback`. Completing OAuth is a deployment
callback, not an agent-facing capability.

Access tokens, refresh tokens, DCR client credentials, and PKCE verifiers
live in a `SecretStore` keyed by the credential resource ID and by opaque
`oauth:session:*` keys. RGAP never stores those values. The same contract
already backs the GitHub credential in `examples/secret-store`. Sharing it
across apps means moving `SecretStore` and `SqliteSecretStore` into
`@rgap/secrets`.

The example hosts a mock authorization server and an `echo` tool so the loop
runs without an external provider. Set `MCP_SERVER_URL` to target any remote
MCP server that speaks protected-resource metadata, PKCE S256, and dynamic
client registration. The complete app lives in `examples/mcp-proxy`.

<Callout type="info">
  The server-level RPC interface is intentionally broad: the caller chooses
  the MCP method. Seal the origin and credential first. Narrow each tool to
  its own resource when a grant must not reach sibling tools.
</Callout>

## MCP server governance

The proxy example creates one resource per MCP server. The next slice places
each tool under that server so grants can select leaves instead of the whole
RPC interface.

```text
acme/
└── mcp/
    ├── google-drive/
    │   └── tools/
    │       ├── search_files
    │       └── read_file
    ├── slack/
    │   └── tools/
    │       ├── search_messages
    │       └── post_message
    └── github/
        └── tools/
            ├── read_issue
            └── create_issue
```

The server resource is the high-level governance boundary. Granting `invoke`
on one tool does not expose its siblings. Granting `invoke` on a server reaches
its current and future tools because a resource entry covers the complete subtree.

<Callout type="info">
  Registering or discovering a tool does not grant access. A grant must contain
  an entry that reaches it with `invoke`.
</Callout>

## Aggregate tools for a coordinator

One coordinator grant can combine selected tools from several servers:

```yaml
name: company/project-coordinator
resources:
  - id: tool_drive_search_files
    permissions: [invoke]
  - id: tool_slack_search_messages
    permissions: [invoke]
  - id: tool_github_create_issue
    permissions: [invoke]
expiresAt: 2026-08-20T23:00:00.000Z
```

The coordinator receives one opaque RGAP token. Provider OAuth tokens, API
keys, and server credentials remain inside the MCP gateway.

## Downscope to a research sub-agent

The coordinator delegates only search tools:

```yaml
name: research-sub-agent
parentId: grant_project_coordinator
resources:
  - id: tool_drive_search_files
    permissions: [invoke]
  - id: tool_slack_search_messages
    permissions: [invoke]
expiresAt: 2026-08-20T22:00:00.000Z
```

The child does not receive the GitHub issue tool and cannot delegate it further.
Its expiration is earlier than the coordinator's expiration.

To enforce application-specific argument restrictions—such as allowed Slack
channels or Drive roots—register each protected scope as a resource and grant
the applicable leaves. Submitted `invoke` entries store `read` as well.
`write`, `invoke`, `bind`, `move`, and `delete` stay independent of each other.

## Gateway request flow

<Steps>
  <Step>
    ### Register trusted resources

    Synchronize MCP servers and tools into the resource tree with stable IDs.
  </Step>
  <Step>
    ### Issue selected authority

    Create a grant with entries for only the coordinator's selected tools and
    issue an opaque bearer.
  </Step>
  <Step>
    ### Filter discovery

    Build `tools/list` from the resources visible through the active grant.
  </Step>
  <Step>
    ### Authorize invocation

    Map the server and tool name to a stable resource ID and require `invoke`
    before retrieving any provider credential.
  </Step>
  <Step>
    ### Delegate with a new token

    Give each sub-agent a child grant and a new bearer rather than sharing the
    coordinator token.
  </Step>
  <Step>
    ### Revoke the branch

    Revoke the coordinator grant to disable it and every descendant agent on
    the next authorization check.
  </Step>
</Steps>

## Tool aggregation in TypeScript

```ts
const coordinator = await companyPlane.grants.create({
  name: 'company/project-coordinator',
  resources: [],
  expiresAt: '2026-08-20T23:00:00.000Z',
});

await coordinator.resources.set([
  { id: driveSearch.id, permissions: ['invoke'] },
  { id: slackSearch.id, permissions: ['invoke'] },
  { id: githubCreateIssue.id, permissions: ['invoke'] },
]);

const coordinatorToken = await coordinator.tokens.create({
  label: 'coordinator',
});
const coordinatorPlane = store.as(coordinatorToken.value);

const researcher = await coordinatorPlane.grants.create({
  name: 'company/project-coordinator/research-sub-agent',
  resources: [],
  expiresAt: '2026-08-20T22:00:00.000Z',
});

await researcher.resources.set([
  { id: driveSearch.id, permissions: ['invoke'] },
  { id: slackSearch.id, permissions: ['invoke'] },
]);
```

The gateway is the policy-enforcement point. The agent cannot bypass its narrow
RGAP grant because it never receives the protected upstream credential.
