RGAP treats MCP servers and their exposed operations as resources. A
deployment registers each trusted server beneath an administrative resource
and assigns stable IDs to servers, tools, prompts, and MCP resources.

## Invoke OpenAI through a resource

Provider credentials stay in deployment configuration. The model name is
sealed executable input, so each resource fixes the model its runtime calls.
The runtime returns only generated text:

```ts
import { createOpenAI } from '@ai-sdk/openai';
import { generateText } from 'ai';

const OpenAIInputSchema = z.object({
  model: z.string(),
  prompt: z.string().min(1),
});

const openai = createOpenAI();
const openaiRuntime: InvokeRuntime<OpenAIInput, OpenAIOutput> = {
  inputSchema: OpenAIInputSchema,
  outputSchema: OpenAIOutputSchema,
  async invoke({ input, signal }) {
    const { text } = await generateText({
      model: openai(input.model),
      prompt: input.prompt,
      abortSignal: signal,
    });
    return { text };
  },
};
```

Creating the executable resource accepts its runtime and sealed literal input
in the same atomic command:

```ts
const model = await admin.resources.create({
  name: 'openai/gpt-5.6-sol',
  executable: {
    runtime: 'openai',
    input: {
      model: 'gpt-5.6-sol',
    },
  },
});

const employeeGrant = await admin.grants.create({
  name: 'company/platform-team/employee',
  bindings: [{ id: model.id, permissions: ['invoke'] }],
  expiresAt: null,
});
const employeeToken = await employeeGrant.tokens.create({ label: 'employee' });
const employee = store.as(employeeToken.value);
const authorizedModel = await employee.resources.get(model.id);

for await (const event of authorizedModel.invoke({
  input: { prompt: 'Summarize why capability attenuation matters.' },
})) {
  console.log(event);
}
```

The employee receives only `invoke` on the executable model resource. Callers
cannot replace its sealed model name. The complete executable version lives in
`examples/openai.ts`.

## Compose a secret-backed resource

A deployment stores each credential under an ordinary RGAP resource ID. An
administrator seals that resource into a trusted executable and exposes only
the executable's narrow interface:

```ts
const githubToken = await admin.resources.create({
  name: 'users/alice/secrets/github-token',
});
await secretStore.set(githubToken.id, process.env.ALICE_GITHUB_TOKEN);

const githubProfile = await admin.resources.create({
  name: 'users/alice/functions/github-profile',
  executable: {
    runtime: 'githubProfile',
    bind: { credential: githubToken.id },
  },
});
```

The `bind` map partially applies top-level input fields with ordinary resource
ID strings. Setting a binding requires `bind` on its resource and records the
authorizing grant lineage. Invocation revalidates that lineage and rejects
caller input that attempts to replace a sealed field.

The trusted runtime reads the credential from the deployment-owned store and
returns only the operation result:

```ts
const githubProfileRuntime = {
  inputSchema: z.object({ credential: z.string() }),
  outputSchema: z.object({ login: z.string() }),
  async invoke({ input }) {
    const token = await secretStore.get(input.credential);
    if (token === undefined) throw new Error('Credential is unavailable.');
    return fetchGithubProfile(token);
  },
} satisfies InvokeRuntime<{ credential: string }, { login: string }>;
```

The administrator gives Alice authority to compose the safe function and to
invoke resources under her scripts subtree, but gives her no authority over
the credential:

```ts
const scripts = await admin.resources.create({ name: 'users/alice/scripts' });
const author = await admin.grants.create({
  name: 'users/alice/script-author',
  bindings: [
    { id: scripts.id, permissions: ['write', 'invoke'] },
    { id: githubProfile.id, permissions: ['bind'] },
  ],
  expiresAt: null,
});
const authorToken = await author.tokens.create({ label: 'script-author' });
```

Alice creates another executable resource and binds the safe function as its
direct dependency:

```ts
const alice = store.as(authorToken.value);
const script = await (await alice.resources.get(scripts.id)).create({
  name: 'profile-summary',
  executable: {
    runtime: 'profileSummary',
    bind: { profile: githubProfile.id },
  },
});

const actingAuthor = await alice.grants.get(author.id);
const consumer = await actingAuthor.create({
  name: 'profile-consumer',
  bindings: [{ id: script.id, permissions: ['invoke'] }],
  expiresAt: null,
});
const consumerToken = await consumer.tokens.create({ label: 'consumer' });
```

The composition runtime invokes that named binding. It receives the profile
result and never receives the transitive credential binding:

```ts
const profileSummaryRuntime = {
  inputSchema: z.object({ profile: z.string() }),
  outputSchema: z.string(),
  async invoke({ input, invoke }) {
    const profile = await invoke.one<{ login: string }>(
      input.profile,
      { input: {} },
    );
    return `GitHub user: ${profile.login}`;
  },
} satisfies InvokeRuntime<{ profile: string }, string>;
```

Creating the `profile` edge requires `bind` on `githubProfile`. When the script
runs, RGAP revalidates that edge and invokes the arbitrary resource ID in
`input.profile`. The profile's frame then revalidates its own credential edge.
This transitive call chain never grants the script's frame direct authority to
bind or read `githubToken`.

The consumer can invoke `script` without receiving `bind` on `githubProfile`.
This is the intended meaning of `bind`: Alice can encapsulate the safe profile
capability and publish her wrapper's interface. Revoking or narrowing
`author` invalidates the recorded `profile` edge on its next invocation and
therefore disables it for every consumer.

The complete Hono app lives in `examples/secret-store`. It uses one SQLite
database for RGAP state and initializes `SqliteSecretStore` with another
SQLite database for secret values. Inputs, outputs, and secret values stay out
of invocation audit records, logs, and errors.

## Invoke an OAuth-protected MCP server

An MCP proxy represents the upstream server, each authenticated connection, and
each credential as separate resources:

```text
acme/
└── mcp/
    ├── servers/
    │   └── github
    ├── connections/
    │   ├── alice-github
    │   └── build-bot-github
    └── credentials/
        ├── alice-github
        └── build-bot-github
```

The server resource identifies a remote Streamable HTTP endpoint without
choosing an identity. A connection combines that server with one OAuth identity.
The credential resource is a stable reference to deployment-owned OAuth state;
its secret value is not repository state.

The connection is an executable resource:

```ts
const connection = await admin.resources.create({
  name: 'acme/mcp/connections/alice-github',
  executable: {
    runtime: 'mcp',
    input: {
      serverUrl: 'https://mcp.example.com',
    },
    bind: {
      credential: credential.id,
    },
  },
});
```

The deployment stores OAuth tokens, registered client information, the PKCE
verifier, and pending authorization state under `credential.id`. The executable
receives only that resource ID. Callers cannot replace the server URL or
credential binding.

## Forward MCP requests

Invoking a connection forwards a client-to-server MCP request:

```ts
for await (const event of authorizedConnection.invoke({
  input: {
    method: 'tools/call',
    params: {
      name: 'create_issue',
      arguments: {
        title: 'Investigate failed deployment',
      },
    },
  },
})) {
  console.log(event);
}
```

The generic input accepts every client-to-server method supported by the
negotiated MCP protocol:

```ts
type McpInvokeInput = {
  method: string;
  params?: Record<string, unknown>;
};
```

The MCP SDK owns connection setup, protocol negotiation, and session lifecycle.
The proxy registers handlers for server-to-client interactions and forwards
caller-selected requests only after RGAP authorizes `invoke` on the connection.
Cancellation of the RGAP invocation cancels the upstream request.

An `invoke` grant on the connection intentionally reaches the complete
capability surface of that authenticated MCP server.

A deployment that accepts user-supplied server URLs validates every redirect
and resolved address, blocks private and link-local destinations, and applies
request timeouts and response-size limits. Deployment configuration may
explicitly permit loopback URLs for local development.

## Complete OAuth in the proxy

The proxy exposes a browser callback independently from the bearer-protected
RGAP command API:

```text
GET /oauth/callback/:flowId
```

The callback loads the pending flow from the credential store, compares the
returned state with the stored value, checks its expiration, and consumes it
exactly once. It then passes the callback parameters to the MCP SDK, which
validates the authorization-server issuer and exchanges the code. The resulting
tokens and client information remain in the credential store.

An OAuth redirect does not call the RGAP invoke endpoint directly. Authorization
servers send browser `GET` requests without an RGAP bearer, while resource
invocation is an authenticated `POST`. The Hono callback is the adapter between
those protocols.

The credential store uses unversioned typed records:

```ts
type McpCredential = {
  tokens?: StoredOAuthTokens;
  clientInformation?: StoredOAuthClientInformation;
  discoveryState?: OAuthDiscoveryState;
  pendingAuthorization?: {
    flowId: string;
    state: string;
    codeVerifier?: string;
    authorizationUrl?: string;
    expiresAt: string;
  };
};
```

Atomic updates prevent simultaneous token refreshes from overwriting each
other. The example SQLite store contains plaintext values and is suitable for
local development only. A deployed proxy supplies an encrypted credential
store through the same interface.

## Downscope MCP authority

The proxy discovers tools, prompts, and MCP resources and can represent them as
children of a connection:

```text
acme/mcp/connections/alice-github/
├── tools/
│   ├── read_issue
│   └── create_issue
├── prompts/
│   └── review_issue
└── resources/
    └── repository
```

Each child is an executable resource with a sealed method and operation name.
Granting `invoke` on a child exposes that operation without exposing its
siblings. Granting `invoke` on the connection reaches all current and future
children because a binding covers the complete subtree.

<Callout type="info">
  Discovering an MCP operation does not grant access. A grant must contain an
  binding that reaches the connection or operation resource with `invoke`.
</Callout>

One coordinator grant can combine selected operations from several
connections:

```yaml
name: company/project-coordinator
bindings:
  - id: tool_drive_search_files
    permissions: [invoke]
  - id: tool_slack_search_messages
    permissions: [invoke]
  - id: tool_github_create_issue
    permissions: [invoke]
expiresAt: 2026-08-20T23:00:00.000Z
```

The coordinator receives one opaque RGAP token. Provider OAuth tokens and
registered client credentials remain inside the MCP proxy.

## MCP proxy request flow

<Steps>
  <Step>
    ### Register the connection

    Create server, credential, and executable connection resources with stable
    IDs.
  </Step>
  <Step>
    ### Authorize the OAuth identity

    Follow the authorization URL and complete the public Hono callback. The
    proxy stores the resulting OAuth state under the credential resource ID.
  </Step>
  <Step>
    ### Issue authority

    Grant `invoke` on the complete connection or on selected operation
    resources, then issue an opaque bearer.
  </Step>
  <Step>
    ### Invoke MCP

    Authorize the RGAP resource, resolve its sealed credential binding, and
    forward the request through an authenticated MCP client session.
  </Step>
  <Step>
    ### Delegate with a new token

    Give each sub-agent a child grant and a new bearer rather than sharing the
    coordinator token.
  </Step>
  <Step>
    ### Revoke the branch

    Revoke the coordinator grant to disable it and every descendant agent on
    the next authorization check.
  </Step>
</Steps>

The complete Hono application lives in `examples/mcp-proxy`.
