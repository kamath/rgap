RGAP is an execution proxy for tools, models, APIs, and MCP servers. An agent
calls an executable resource with an RGAP bearer. The proxy checks whether that
bearer can invoke the resource, adds deployment-owned credentials, and sends the
request upstream.

The agent gets the result without receiving an OAuth token, API key, refresh
token, or other provider credential.

## What happens when an agent invokes a resource

1. The agent sends input, an executable resource ID, and its RGAP bearer.
2. RGAP resolves the bearer and authorizes `invoke` against the complete grant
   lineage.
3. The runtime receives the resource's sealed definition and explicitly bound
   resources. Deployment-owned credentials stay inside the proxy.
4. The runtime calls the upstream service and streams events back to the agent.

This keeps authorization and credential handling at the network boundary. The
agent cannot turn a purpose-built executable into an unrestricted authenticated
proxy by replacing its upstream URL, credential binding, or other sealed
configuration.

## Why use the proxy

- **Keep secrets out of agent context.** Provider credentials live in a
  deployment-owned store and never appear in prompts or invocation input.
- **Expose useful operations, not raw credentials.** A resource can represent
  one tool, one model, one MCP connection, or a carefully designed composition.
- **Narrow access for each task.** A bearer reaches only the executable
  resources granted to it.
- **Stop access immediately.** Revoking a grant disables its bearer and every
  descendant on the next invocation.
- **Compose calls safely.** An executable can invoke explicitly bound resources
  without passing their credentials or broad authority to the caller.

## The four pieces

| Piece | What it does |
| --- | --- |
| **Executable resource** | Seals the runtime and deployment-controlled configuration behind a stable ID. |
| **Binding** | Gives a runtime explicit access to another RGAP resource it needs. |
| **Grant** | Selects which resources and operations a caller may use. |
| **Bearer** | Lets a caller exercise one grant without exposing upstream credentials. |

Resources and grants form hierarchies so access can be delegated to agents and
sub-agents without becoming broader. Read [Core concepts](/docs/concepts) when
you need the full model.
