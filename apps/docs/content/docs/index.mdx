RGAP is a protocol for organizing resources and authority across teams,
applications, tools, and services. Resources follow a familiar hierarchy,
grants reflect how an organization delegates control, and each bearer carries a
narrow, revocable slice of that authority.

The same protocol provides an execution proxy for tools, models, APIs, and MCP
servers. A caller invokes an executable resource with an RGAP bearer; the proxy
checks its authority, adds deployment-owned credentials, and sends the request
upstream. The caller gets the result without receiving an OAuth token, API key,
refresh token, or other provider credential.

## What happens when a caller invokes a resource

1. The caller sends input, an executable resource ID, and its RGAP bearer.
2. RGAP resolves the bearer and authorizes `invoke` against the complete grant
   lineage.
3. The runtime receives the resource's sealed definition and explicitly bound
   resources. Deployment-owned credentials stay inside the proxy.
4. The runtime calls the upstream service and streams events back to the caller.

This keeps authorization and credential handling at the network boundary. The
caller cannot turn a purpose-built executable into an unrestricted authenticated
proxy by replacing its upstream URL, credential binding, or other sealed
configuration.

## Why use the proxy

- **Keep secrets out of application context.** Provider credentials live in a
  deployment-owned store and never appear in caller-controlled invocation
  input.
- **Expose useful operations, not raw credentials.** A resource can represent
  one tool, one model, one MCP connection, or a carefully designed composition.
- **Narrow access for each task.** A bearer reaches only the executable
  resources granted to it.
- **Stop access immediately.** Revoking a grant disables its bearer and every
  descendant on the next invocation.
- **Compose calls safely.** An executable can invoke explicitly bound resources
  without passing their credentials or broad authority to the caller.

## The four pieces

| Piece | What it does |
| --- | --- |
| **Executable resource** | Seals the runtime and deployment-controlled configuration behind a stable ID. |
| **Binding** | Gives a runtime explicit access to another RGAP resource it needs. |
| **Grant** | Selects which resources and operations a caller may use. |
| **Bearer** | Lets a caller exercise one grant without exposing upstream credentials. |

Resources and grants form hierarchies so authority can follow an organization's
teams, services, workflows, and delegated operators without becoming broader.
Read [Core concepts](/docs/concepts) when you need the full model.
