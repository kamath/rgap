RGAP is a protocol for organizing resources and authority across teams,
applications, tools, and services.

Use it to put one consistent, programmable boundary in front of anything your
users or software can access. RGAP combines hierarchical resources, delegated
grants, opaque bearers, and an execution proxy, so the same protocol can protect
a model catalog, an MCP deployment, internal functions, or a complete
organization.

## One protocol, several gateways

### Streaming, OpenAI-compatible model access

Expose a streaming OpenAI-compatible proxy while RGAP gates each request to the
models its caller can access. RBAC and scoped grants support policies for a
complete catalog, one provider, or one model, and the proxy adds provider
credentials only after RGAP authorizes the call.

### MCP access without credential sharing

Represent an MCP server, authenticated connection, and discovered operations in
one resource hierarchy. Grant `invoke` on the connection for complete access or
on selected child resources for specific tools, prompts, and resources. OAuth
tokens, refresh tokens, and session state stay in the gateway.

### Secure functions and compositions

Turn a function into an executable resource with a sealed runtime definition.
Its public input stays separate from deployment-controlled configuration and
bound resources. A function can call explicitly bound models, APIs, or other
functions without giving that broader authority to its caller.

### Authority that follows the organization

Resource paths organize what exists; grant paths organize who can act. A
company can delegate to a division, team, service, or temporary workflow, and
every descendant is mechanically constrained to the authority of its
ancestors. Revoking one grant stops its complete descendant tree on the next
authorization check.

## How an invocation works

1. The caller sends input, an executable resource ID, and its RGAP bearer.
2. RGAP resolves the bearer and checks `invoke` through its complete grant
   lineage.
3. The execution proxy loads the resource's sealed definition and the protected
   resources explicitly bound to it.
4. The runtime performs the operation and streams its result back to the
   caller.

The caller never receives the provider key, OAuth token, or secret used by the
runtime. It also cannot replace sealed details such as the upstream service,
model, credential binding, or function implementation.

## The protocol underneath

| Piece | What it does |
| --- | --- |
| **Resource** | Gives a model, tool, function, service, or organizational object a stable identity in a hierarchy. |
| **Grant** | Selects resources and permissions, then delegates only equal or narrower authority. |
| **Bearer** | Lets a caller exercise one grant through an opaque, revocable credential. |
| **Executable definition** | Seals how a callable resource runs and which configuration the caller cannot override. |
| **Binding** | Gives an executable explicit access to another protected resource it needs. |

The authorization model and execution proxy use the same resource identities,
so moving or renaming an object does not invalidate grants or integrations.
