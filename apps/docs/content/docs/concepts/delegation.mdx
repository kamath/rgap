title: Delegation and attenuation
description: How child grants prove they never expand their parent's authority.

---

Delegation creates a child grant beneath the acting grant. Every child resource
entry must be covered by a parent resource entry.

```text
Alice: read/write/delete projects/alpha
└── Bob: read projects/alpha/docs
    └── Carol: read projects/alpha/docs/design
```

Bob cannot grant write access, reach outside `projects/alpha/docs`, or create a
child that outlives Bob's grant.

## Resource entries

A grant aggregates one or more resource entries:

```ts
type GrantResource = {
  id: ResourceId;
  permissions: Permission[];
};
```

Each entry names exactly one target. Multiple entries let a grant combine
authority from separate branches, such as selected tools from several MCP
servers.

## Coverage

`covers(parent, child)` holds when the child's location is inside the parent's
location and every child permission appears in the parent's permission set.

```ts
covers(parent, child, resources) =
  isWithin(resources, child.id, parent.id) &&
  child.permissions.every((permission) =>
    parent.permissions.includes(permission),
  );
```

Both entries target live resources by stable ID. Coverage compares their
current ancestry in the resource tree.

<Callout type="info" title="Permissions are plain sets">
  No permission implies another. `write` does not imply `read`, and `read` is
  not included by holding any other permission.
</Callout>

## The complete lineage matters

Issue-time containment is necessary but not sufficient. Every authorization
decision also checks each ancestor grant against the requested resource in the
current tree.

Suppose a descendant grant targets a resource by ID and that resource moves
outside an ancestor's scope. The descendant entry follows the identity, but the
ancestor no longer covers the requested location. Authorization denies until
the complete lineage covers the resource again.

## Amending a grant

A grant's identity, parent, and expiration are fixed at creation. Its resource
set may be replaced atomically.

The replacement set must satisfy the same containment proof as a newly created
grant. Any direct child no longer covered by the new set is revoked together
with its descendants.

```text
Before                         After parent narrows

Team: docs + tools             Team: docs
├── Writer: docs               └── Writer: docs
└── Runner: tools                  Runner: revoked
```

## Empty grants

A grant may start with an empty resource set and authorize nothing. This lets
an application record a delegation before deciding what authority it reaches.
Setting resources later still requires the parent coverage proof.
