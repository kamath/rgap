Resources form a file tree. A resource is either a folder or an executable.
Folders organize the tree and may have children. Executables contain their
runtime definition and are always terminal resources.

```ts
type ResourceBase = {
  id: ResourceId;
  parentId: ResourceId | null;
  name: string;
  deletedAt: string | null;
};

type Folder = ResourceBase & {
  executable: null;
};

type ExecutableResource = ResourceBase & {
  executable: ExecutableDefinition;
};

type Resource = Folder | ExecutableResource;
```

An empty folder remains a folder even though it currently has no children.
Resource type follows the `executable` field rather than the current child
count, and it is decided once when the resource is created.

## Create at a path

Create accepts a slash-separated location in `name`. The path is the location,
so the write does not include a parent ID. Collection create walks from the
forest root. Handle create walks from that resource. Missing live prefixes are
created, and the command returns the leaf.

```ts
const design = await admin.resources.create({
  name: 'acme/platform/docs/design',
  executable: {
    runtime: 'renderDesign',
  },
});
```

`design.name` is `design`. `design.parentId` is the `docs` resource. The
derived path of `design` is `acme/platform/docs/design`. Missing `acme`,
`platform`, and `docs` prefixes are folders. The returned `design` resource is
executable.

The same command creates a relative path under an existing resource:

```ts
const platform = await admin.resources.create({ name: 'acme/platform' });
const design = await platform.create({
  name: 'docs/design',
  executable: { runtime: 'renderDesign' },
});
```

Each stored resource name is one segment. Missing prefixes become ordinary
folders. Live folder prefixes are reused. An executable cannot be traversed or
receive children. The leaf must be absent: a second create at an occupied path
fails with `duplicate_path`.

Create is one state transition. Each newly created resource is audited as
`resource.create` and receives a stable ID minted from its segment name.

Creating a new root resource is administrative. Creating a child requires
`write` on that child's parent. `store.as(token).resources.create` walks from
the forest root: it refuses a path that would create a new root, and it
requires `write` on the parent of every resource it creates. Existing prefixes
need no additional permission.

## Update

`resource.update` changes a resource's name, parent, or both atomically:

```ts
const updated = await design.update({
  name: 'architecture',
  parentId: platform.id,
});
```

An update must provide at least one field. `name` and `parentId` are the only
updatable fields. Renaming requires `write` on the resource. Reparenting
requires `move` on the resource and `write` on the destination folder.

## Sealed executables

A resource's `executable` is fixed by create. A folder never becomes an
executable, an executable never becomes a folder, and an executable keeps the
runtime, sealed input, and bindings it was created with for its whole
lifetime.

Publish different behavior by creating a new executable resource and deleting
the one it replaces:

```ts
const architecture = await platform.create({
  name: 'docs/architecture',
  executable: { runtime: 'renderArchitecture', input: { format: 'markdown' } },
});
await design.delete();
```

The replacement is a distinct resource with its own ID. Grant-resource entries
and bindings that named the deleted resource stay pointed at the tombstone and
become permanently ineffective, so authority is re-granted deliberately rather
than inherited by a definition that was swapped underneath it.

## Identity and location

A resource's ID names the object wherever it moves. Its path describes its
current location and is derived from its ancestry.

```text
projects/alpha/secret
        ↓ move
projects/private/secret
```

A grant binding targeting `secret` follows it to
`projects/private/secret`. Grant bindings always use stable resource
IDs, so a binding never transfers authority to a different object that later
occupies the old location.

## Subtree semantics

Every grant binding reaches its target and all current descendants. A grant on
a folder therefore includes children created later.

<Callout type="info">
  Grant executable resources instead of a folder when future children must not
  inherit the binding's authority.
</Callout>

## Path normalization

Paths are canonicalized by splitting on `/`, trimming segments, and discarding
empty segments. `Acme`, `Acme/`, and `/Acme//` identify the same location.

Resource and grant creation accept presentation paths and materialize them in
their respective trees. Other operational commands and grant bindings
use stable IDs.

## Deletion

Deletion marks a resource and all descendants as deleted. Records remain as
tombstones so IDs are never reused.

Deleting an executable means deleting its resource. There is no independent
executable deletion operation, and deletion is the only way to retire a
definition.

- Deleted resources appear in no listing.
- No path resolves to a deleted resource.
- Commands and authorization cannot target a deleted resource.
- A deleted name may be reused under the same parent by a new resource with a
  new ID.

This preserves the meaning of grant bindings and audit events without
reserving names forever.
