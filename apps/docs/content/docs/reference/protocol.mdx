This page is the normative definition of RGAP. Authorization and metadata
transitions are expressed over one immutable state value. An implementation
conforms when, given the same state and request, it reaches the same decision.
Invocation additionally depends on the same deployment-owned runtime registry.

## Records

State is three normalized collections plus an ordered audit log.

```ts
type State = {
  resources: Record<string, Resource>;
  grants: Record<string, Grant>;
  tokens: Record<string, Token>;
  audit: AuditEvent[];
};
```

```ts
type ResourceBase = {
  id: string;
  parentId: string | null;
  name: string;
  deletedAt: string | null;
};

type Folder = ResourceBase & {
  executable: null;
};

type ExecutableResource = ResourceBase & {
  executable: ExecutableDefinition;
};

type Resource = Folder | ExecutableResource;

type GrantBinding = {
  id: string;
  permissions: Permission[];
};

type Grant = {
  id: string;
  name: string;
  parentId: string | null;
  bindings: GrantBinding[];
  expiresAt: string | null;
  revokedAt: string | null;
};

type Token = {
  id: string;
  grantId: string;
  label: string;
  hash: string;
  expiresAt: string | null;
  revokedAt: string | null;
};

type ExecutableBinding = {
  resourceId: string;
  grantLineage: string[] | null;
};

type ExecutableDefinition = {
  runtime: string;
  input: Record<string, JsonValue>;
  bind: Record<string, ExecutableBinding>;
};

type AuditEvent = {
  id: string;
  at: string;
  action: string;
  target: string;
  result: 'allowed' | 'denied' | 'recorded';
  detail: string;
};
```

`Permission` is `'read' | 'write' | 'delete' | 'move' | 'invoke' | 'bind'`. Every
persisted record is JSON-compatible. Timestamps are RFC 3339 strings in UTC
with a fixed number of fractional digits so lexical comparison preserves time
order.

## Identity and location

A resource's ID is assigned once and never changes. Its path is derived by
joining the names of its ancestors and itself with `/`.

```ts
resourcePath(resources, id) =
  [...ancestors(id), id]
    .map((each) => resources[each].name)
    .join('/');
```

Paths are canonicalized by splitting on `/`, trimming each segment, and
discarding empty segments. The empty path names nothing.

Resource commands use stable IDs after path-based creation resolves or
materializes a location. Grant bindings always target stable IDs.

### Ancestry

```ts
isWithin(resources, id, rootId) =
  id === rootId ||
  (parentId(id) !== null &&
    isWithin(resources, parentId(id), rootId));
```

`isWithin` is reflexive. Implementations detect a repeated parent while walking
the tree and raise `resource_cycle`.

### Tombstones

Deletion marks a resource and its live descendants with `deletedAt`. Tombstones
are not live and are excluded from listings, grant-binding validation,
authorization, and guarded views.

Records remain so stable IDs are never reused. Sibling-name uniqueness considers
only live resources, so a new resource may reuse a deleted name with a new ID.

## Permissions

| Permission | Authorizes |
| --- | --- |
| `read` | Reading a resource and listing its children. |
| `write` | Modifying a resource and creating children under it. |
| `invoke` | Calling a resource, such as executing a tool. |
| `bind` | Sealing a resource into another executable as a direct dependency. |
| `move` | Relocating a resource to a different parent. |
| `delete` | Deleting a resource together with its descendants. |

A grant binding always includes `read`. A write accepts any non-empty
permission set and stores that set unioned with `read`, in canonical order:

```ts
normalizePermissions(submitted) =
  ['read', 'write', 'invoke', 'bind', 'move', 'delete']
    .filter((permission) =>
      permission === 'read' || submitted.includes(permission),
    );
```

Submitting `['invoke']` stores `['read', 'invoke']`. Submitting `['read']`
stores `['read']`.

No permission implies another during authorization. `write`, `invoke`, and
`bind` remain independent, and `delete` does not include `move`. `authorize`
tests membership in the stored set.

| Operation | Required authority |
| --- | --- |
| Read a resource or list children | `read` on the resource |
| Invoke a resource | `invoke` on the resource |
| Bind a resource into a new executable | `bind` on the bound resource |
| Read a resource's executable definition | `read` on the resource |
| Update a resource's name | `write` on the resource |
| Create a child | `write` on that child's parent |
| Create at a path | `write` on the parent of each created resource |
| Update a resource's parent | `move` on the resource and `write` on the destination folder |
| Delete a subtree | `delete` on its root |
| Delegate a grant | The child downscopes the acting grant |
| Create at a grant path | The parent of each created grant is the acting grant or a descendant of it |
| Set a grant's bindings | The new set downscopes the grant's parent |
| Issue or revoke a token | The grant is acting or delegated from acting |
| Revoke a grant | The grant is acting or delegated from acting |

Creating a new root resource, moving a resource to a root, creating a root
grant, and setting a root grant's bindings are administrative operations.

## Grant-binding algebra

Two relations define the model: what one grant binding authorizes and
when one entry contains another.

### Authorization by one entry

```ts
authorizes(entry, resources, resourceId, permission) =
  entry.permissions.includes(permission) &&
  isLive(resources[entry.id]) &&
  isWithin(
    resources,
    resourceId,
    entry.id,
  );
```

### Containment

`covers(parent, child)` holds when every request the child entry authorizes is
also authorized by the parent entry.

```ts
covers(parent, child, resources) =
  isLive(resources[parent.id]) &&
  isLive(resources[child.id]) &&
  isWithin(resources, child.id, parent.id) &&
  child.permissions.every((permission) =>
    parent.permissions.includes(permission),
  );
```

Coverage follows current resource ancestry. Moving a targeted resource can
therefore change whether one entry covers another without changing either
entry's stable target.

## Grants

### Validity at creation

A grant is created only when:

1. Its stored name is a single non-empty segment and contains no `/`.
2. Every binding has one stable resource ID and a non-empty permission
   set that includes `read`.
3. Every targeted resource is live.
4. Its parent exists and is active, or the grant is a root.
5. It does not outlive its parent.
6. Every child binding is covered by a parent binding.
7. No other active grant has the same parent and name.

The binding set may be empty and authorize nothing.

### Create at a path

Create accepts a slash-separated location. The write is the path; it does not
include a parent ID. Collection create walks from the grant forest root. Handle
create walks from that grant. The path is normalized by splitting on `/`,
trimming segments, and discarding empty segments. After normalization the path
must contain at least one segment.

The command walks the path in one state transition. Each stored grant name is
one segment and contains no `/`. Active prefixes are reused. Missing prefixes
are created as ordinary grants with the submitted binding set and expiration.
Each created record stores the parent ID derived from that walk. The leaf must
not already exist; an occupied path is `duplicate_path`.

Each newly created grant receives an unused ID minted from its segment name
and is audited as `grant.create` or `grant.delegate`. Creating a new root is
administrative.

For a token-plane collection create, the walk must resolve existing active
ancestors from the forest root until it reaches the acting grant's stable ID.
No segment may be created before that ID is reached. After it is reached, every
existing segment must remain within the acting grant's subtree and every
created grant's parent must be the acting grant or a descendant of it. A handle
create starts at that handle and requires the handle to be the acting grant or
a descendant. Each created child independently satisfies the creation validity
rules against its immediate parent.

### Setting bindings

Setting a grant's bindings atomically replaces the whole set.

1. The grant exists and is active.
2. Every replacement entry is structurally valid.
3. Every entry is covered by the parent when one exists.
4. Every direct child no longer covered by the replacement is identified.
5. Each identified child and all descendants are revoked.
6. The replacement, revocations, and audit event commit together.

### Activity and lineage

```ts
isActive(record, now) =
  record.revokedAt === null &&
  (record.expiresAt === null || record.expiresAt > now);

lineage(grants, grantId) =
  [grants[grantId], ...lineage(grants, grants[grantId].parentId)];
```

The lineage runs from the selected grant to its root. A missing ancestor is
`missing_parent`; a repeated ancestor is `grant_cycle`.

Revoking a grant timestamps it and every descendant grant. Revoking a token
timestamps only that token.

## Tokens

A token is an opaque bearer string. Implementations store only a
preimage-resistant hash and compare the hash of a presented bearer. A token
does not outlive its grant and grants no authority of its own.

The guard resolves a presented bearer to its active token and complete active
grant lineage. Bearer resolution is internal to the store and is not a
repository or HTTP operation. An unknown, expired, or revoked token, or an
inactive grant in its lineage, rejects the guarded command as unauthorized.

## Decision procedure

`authorize(state, tokenHash, resourceId, permission, now)` returns:

```ts
type Decision = {
  allowed: boolean;
  detail: string;
  grantId: string | null;
  lineage: string[];
};
```

The procedure:

1. Deny when the target resource is not live.
2. Find the token by hash and deny when it is missing or inactive.
3. Compute the selected grant's lineage and deny when any grant is inactive.
4. For each grant, look for an entry that authorizes the concrete request.
5. Allow only when every grant has such an entry.

```ts
allowed = chain.every((grant) =>
  grant.bindings.some((binding) =>
    authorizes(binding, resources, resourceId, permission),
  ),
);
```

Authority is the intersection of the complete lineage in the current resource
tree.

### Guarded views

`store.as(token)` returns a guarded repository. Resource collection reads
always name one parent ID or `null`; there is no unscoped flat resource list.
The administrative plane lists every live root for `parentId: null`. A guarded
plane lists only the live top-level ancestors that lead to one of the acting
grant's binding resource IDs.

Every grant binding carries `read`, and each child grant binding is contained
by a binding on every ancestor grant. For a contextual ancestor above a bound
resource, a guarded child read contains only the next live children on paths
toward bound resources. At or below a bound resource, it contains the requested
parent's live children. Callers recursively page these parent-scoped reads to
present the visible hierarchy.

The guard follows parent links from grant targets and requested parents. It
does not enumerate a complete visible subtree, unrelated resource branches, or
a resource-permission matrix. Grant, token, and audit collections are filtered
to the acting grant's lineage and delegated branch.

Call `authorize` when an explicit decision for one resource and permission is
required.

## Resource operations

Every operation computes and commits one complete state transition with its
audit event.

### Create

Create accepts a slash-separated location. The write is the path; it does not
include a parent ID. Collection create walks from the forest root. Handle
create walks from that resource. The path is normalized by splitting on `/`,
trimming segments, and discarding empty segments. After normalization the path
must contain at least one segment.

The command walks the path in one state transition. Each stored resource name
is one segment and contains no `/`. Live prefixes are reused. Missing prefixes
are created as folders. Each created record stores the parent ID derived from
that walk. An executable prefix is not traversable and cannot receive a child.
The leaf must not already exist; an occupied path is `duplicate_path`.

Each newly created resource receives an unused ID minted from its segment name
and is audited as `resource.create`. Creating a new root is administrative.
Creating a child requires `write` on that child's parent.

Create without `executable` creates a folder leaf. Create with an `executable`
containing `runtime`, optional sealed `input`, and optional `bind` creates an
executable leaf. The command validates the registered runtime, sealed input,
live binding targets, and `bind` authority before it commits any resource.
Administrative create records administrative binding provenance.

### Update

Update accepts at least one of `name` or `parentId` and changes all supplied
fields in one transition. `name` is one non-empty path segment. A new
`parentId` must identify a live folder, and the move must not create a cycle or
duplicate path. Updating `parentId` never rewrites or revokes grants.

`executable` is not an update field. A resource's kind and executable
definition are sealed by create and never change, so a folder never becomes an
executable and an executable never converts into a folder or gains a different
definition.

Renaming requires `write` on the resource. Reparenting requires `move` on the
resource and `write` on the destination folder. The update validates every
applicable condition and commits one resource record and audit event
atomically.

### Delete

Deletion finds the live subtree, marks every member with `deletedAt`, and
commits atomically. Grant bindings naming deleted resources become permanently
ineffective. Deleting an executable means deleting the complete resource;
executable definitions have no independent delete operation.

## Executables

An executable resource contains one registered runtime definition and remains
the authorization target. Its definition can seal JSON-compatible top-level
input values and pre-bind other top-level fields to ordinary resource ID
strings. Configured and bound fields are sealed rather than caller-controlled
invocation values.

Resource create is the only operation that defines an executable. It trims and
validates the runtime name, requires that runtime to be registered, requires
`bind` on every directly bound resource, and atomically stores the resource
together with its audit event. Each binding records the complete grant lineage
that authorized it. Administrative bindings record administrative provenance.

Configured and binding names are top-level input property names and must be
unique across both maps. `__proto__`, `prototype`, and `constructor` are
invalid names. Invocation rejects caller input containing any configured or
bound name, inserts both sets of sealed fields, and parses the complete input
with the runtime schema.

Binding creation validates authority immediately, and every invocation
revalidates that the bound resource is live and its recorded lineage remains
active and still covers `bind`. Revoking or narrowing any grant in that
lineage disables the edge.

A valid binding is deliberately delegable through its executable. Any
principal with `invoke` on that executable can exercise its interface without
holding `bind` on the direct target. Granting `bind` therefore authorizes the
holder to create a wrapper and publish that wrapper by delegating `invoke`.

Authority composes through nested invocation frames. If A binds B and B binds
C, invoking A can invoke B, whose own frame can then use C. Authority is not
flattened: A's frame does not gain a direct edge to C. Every hop is revalidated
when the call chain runs.

Bindings are references to resource identity. A frame resolves the target's
sealed executable definition and revalidates that the target is live. Because
that definition never changes, no principal can alter the behavior observed
through an existing binding; behavior changes only through the deployment's
registered runtime implementation.

An executable definition cannot be replaced or removed independently. Retiring
one requires `resource.delete`, which tombstones the complete resource and
permanently disables every executable binding and grant binding naming it.
Publishing a different definition means creating another executable resource
with its own ID. Reading the embedded definition requires `read`; deleting the
resource requires `delete`.

The runtime registry is immutable deployment configuration from the
repository's perspective. Repository commands cannot register, replace, or
configure runtime code. RGAP defines no built-in runtime implementation.

## Generic invocation

```ts
type InvokeInput = {
  input: unknown;
};

type InvocationEvent =
  | { type: 'data'; value: unknown }
  | { type: 'done' };

type RuntimeResult<T> = T | AsyncIterable<T>;

type RuntimeSchema<T> = {
  parse(value: unknown): T;
};

type RuntimeInvocation<TInput> = {
  input: TInput;
  invoke: {
    stream(resourceId: string, input: InvokeInput): AsyncIterable<InvocationEvent>;
    one<T = unknown>(resourceId: string, input: InvokeInput): Promise<T>;
  };
  signal: AbortSignal;
};

interface InvokeRuntime<TInput = unknown, TOutput = unknown> {
  inputSchema: RuntimeSchema<TInput> | null;
  outputSchema: RuntimeSchema<TOutput> | null;
  invoke(
    context: RuntimeInvocation<TInput>,
  ): RuntimeResult<TOutput> | Promise<RuntimeResult<TOutput>>;
}
```

Invocation is one ordered decision and lifecycle:

1. Resolve the executable definition and registered runtime.
2. Authorize `invoke` on the executable resource through the complete lineage.
3. Revalidate every sealed binding's live target and recorded `bind` lineage.
4. Require object input when bindings exist and reject any caller-supplied
   property whose name is sealed.
5. Create input without prototype inheritance, insert the bound resource ID
   strings, then parse the complete input when the runtime's `inputSchema` is
   not null.
6. Invoke the runtime with typed input, an abort signal, and nested invocation
   methods that accept resource IDs.
7. Authorize each nested target from either the initiating caller's direct
   `invoke` authority or a valid direct binding edge on the current frame.
8. Reject a resource already present in the active invocation stack and reject
   a call deeper than 32 frames.
9. Normalize one value, a promise, an async iterable, or `undefined`.
10. Parse each output when `outputSchema` is not null, emit a `data` event for
   each defined value, and emit `done` automatically.
11. Let runtime failures terminate the stream. Record normal exhaustion as
   `done`, runtime failure as `error`, and caller abort or early iterator return
   as `cancelled`.

Runtimes return raw values and never construct protocol events. The registry
accepts heterogeneous generic runtimes; type erasure is confined to registry
lookup. Cancellation propagates through nested calls and reaches each runtime
through `AbortSignal`. Every nested invocation produces its own audit record,
linked to the parent invocation without recording inputs or outputs.
Authorization is fixed for the lifetime of one frame. Authorization state is
read again when a nested frame starts.

A schema can accept a bound ID in any string field. Binding a resource to the
wrong same-type field is a configuration error rather than an authorization
failure; the runtime's complete schema and behavior determine whether it
fails. RGAP assigns resource semantics only to fields named in `bind`.

## Invocation auditing and redaction

An invocation record contains the executable resource ID, runtime name,
grant-lineage IDs, parent invocation ID when present, binding resource IDs,
start and finish times, and result (`done`, `error`, or `cancelled`). It does
not contain invocation input, output data, or external secret values.
Implementations apply the same rule to logs and errors.

## Enforcement boundary

Stores expose no unrestricted command methods directly:

- `store.as(token)` returns commands authorized by the bearer.
- `store.admin()` returns unrestricted commands for trusted infrastructure.

The token plane enforces operation authority before forwarding each command.
The administrative plane enforces protocol invariants without token checks.
Both expose the same repository interface.

## Conformance

An implementation conforms when:

1. Stable IDs are assigned once and never reused.
2. Paths are derived and canonicalized as defined.
3. Grant-binding permission sets always include `read` and are compared as
   plain sets with no implication.
4. Grant bindings target live resources by stable ID.
5. `covers` implements current-tree containment exactly.
6. Grant creation and amendment prove attenuation.
7. Authorization checks the complete grant lineage.
8. Revocation cascades through descendant grants.
9. Resource operations and grant amendments commit atomically with audit.
10. Deleted resources remain as unreadable tombstones.
11. Commands are exposed only through explicit token or administrative planes.
12. Every resource is a folder or executable; only folders have children, every
    executable contains its definition, and create fixes that kind for the
    resource's lifetime.
13. Creating an executable binding requires `bind` on its direct resource
    through the complete lineage and records that lineage with the edge.
14. Invocation revalidates every binding lineage and live target before
    inserting sealed resource ID strings into runtime input.
15. An executable definition is written only by the create that seals it, is
    never modified afterward, and is removed only by deleting its resource.
16. Binding authority is delegable through `invoke`, follows the target's
    sealed executable definition while the target stays live, and never
    flattens transitive edges into a caller.
17. Runtime registration, schemas, and behavior are deployment configuration
    that repository commands cannot mutate.
18. Invocation resolves one runtime, rejects sealed input collisions, parses
    input after safely inserting bound fields,
    authorizes arbitrary nested resource IDs against caller authority or the
    current frame's direct edges, follows valid edges transitively across
    frames, rejects active cycles and depths above 32, normalizes results into
    `data` and automatic `done` events, propagates cancellation, and records
    each call in the chain.
19. Audit records, errors, and logs exclude inputs and outputs while retaining
    the IDs, runtime, timing, and result needed for accountability.
20. An implementation may load and persist command-scoped records when the
    command remains atomic and observably equivalent to one complete state
    transition.
