The repository implements RGAP as framework-neutral TypeScript rules, durable
SQLite persistence, deployment-owned executable runtimes, a Hono HTTP server,
an executable scratchpad, and this MDX documentation application.

```text
packages/
├── core/                 # authorization, executable orchestration, and contracts
├── store/
│   └── sqlite/           # Drizzle and SQLite RGAP implementation
├── secret-store/
│   ├── src/index.ts      # secret-store interface
│   └── sqlite/           # local SQLite secret persistence
├── oauth-store/
│   ├── src/index.ts      # OAuth callback-flow interface
│   └── sqlite/           # local SQLite callback-flow persistence
└── examples/
    └── mcp-proxy/        # mountable Hono MCP and OAuth adapter
apps/
├── server/         # Hono HTTP API and generated clients
└── docs/           # Next.js and Fumadocs documentation
examples/
├── index.ts        # executable scratchpad
└── invariants.ts   # executable invariant walkthrough
tests/
└── invariants/     # property and state-machine verification
```

## Core boundary

`@rgap/core` separates five modules:

- `domain.ts` defines folder and executable resources, grants, tokens, audit
  events, permission algebra, and pure resource and grant rules.
- `repository.ts` defines `RgapCommands`, `RgapStore`, `RgapRepository`, and
  resource, grant, and token handles.
- `guard.ts` constructs the bearer-token command plane and enforces visibility
  and command authority.
- `executable.ts` validates embedded executable definitions and sealed input
  bindings, records and revalidates binding authority, and orchestrates nested
  invocation.
- `runtime.ts` defines structural runtime schemas, typed invocations and
  results, invocation events, nested resource invocation, and `RuntimeRegistry`.

A store exposes only `as(token)` and `admin()`. Either method returns a
repository whose collections mint and look up handles.

Handles combine record fields with applicable commands:

- A folder creates descendants at a relative path. Every resource updates and
  deletes itself, and executable resources can be invoked.
- A grant creates descendants at a relative path, replaces bindings,
  issues tokens, and revokes.
- A token revokes.

Adapters implement an ID-based `RgapCommands` sink.
`repositoryFrom(commands)` builds the handle surface. Resource and grant create
accept a slash-separated location and materialize missing prefixes. Path
rendering and normalization remain pure helpers.

### Repository planes

`store.as(token)` returns a guarded repository. Its commands authorize the
required permission before forwarding and reject with the decision detail.

`store.admin()` returns an unrestricted repository for trusted bootstrap and
operations code. Both planes share the same interface.

```ts
const repository = store.as(token);
const admin = store.admin();
```

### Reads

Focused collection queries list resources, grants, tokens, and audit events.
They return ordered arrays of serializable records with bounded page sizes and
keyset cursors. A caller never needs to load the complete store.

Every resource list query includes `parentId`, including `null` for a root
page. There is no unscoped resource list. The guarded plane derives contextual
ancestor edges by following parent links from the acting grant's binding
resource IDs.
For a requested parent, it either returns those contextual child edges or
forwards one parent-filtered page when the parent sits at or below a grant
target. Direct resource reads use the same bounded ancestry check. No guarded
read materializes or sorts the complete visible subtree.

This traversal uses ordinary ID and parent-filtered repository reads. Its work
is proportional to grant bindings, ancestry depth, and the requested page; it
does not require recursive SQL.

Storage adapters also load command-scoped records for mutations and
authorization decisions. The core rule still receives every record needed to
decide the command, while unrelated resources, grants, tokens, and audit events
remain outside the transaction's working set.

Ordinary commands are asynchronous and JSON-compatible. Invocation returns
`AsyncIterable<InvocationEvent>`, where events are `data` or `done`; runtime
failures terminate the iterable.

### TypeScript identities

The TypeScript surface brands identifiers that remain ordinary strings at
runtime and on the wire:

| Type | Used for |
| --- | --- |
| `ResourceId` | Resource records, grant-binding targets, and move destinations. |
| `GrantId` | Grant records, grant ancestry, and token grant references. |
| `TokenId` | Stored token-record identity. |
| `TokenValue` | The one-time bearer accepted by `store.as` and `authorize`. |
| `TokenHash` | The bearer hash stored on a token record. |

Repository reads return branded values. Seed data and tests that construct
records directly use `resourceId`, `grantId`, `tokenId`, `tokenValue`, and
`tokenHash`. Paths remain ordinary strings for resource creation and rendering;
grant bindings use `ResourceId`.

## Deployment-owned runtimes

The SQLite store accepts deployment-owned runtime configuration:

```ts
new SqliteRgapStore({
  url,
  runtimes,
});
```

Each heterogeneous `InvokeRuntime<TInput, TOutput>` owns nullable structural
input and output schemas and its invocation implementation. The schemas expose
`parse(value: unknown)`, so Zod schemas work directly without a core dependency
on Zod. Runtime registration and behavior are not repository state.

## Store interfaces

Storage contracts live with their domains instead of in a shared interfaces
package. `@rgap/secret-store` exports `SecretStore<T>`.
`@rgap/oauth-store` exports `OAuthFlowStore` and `OAuthFlowRecord`. Neither
interface package chooses persistence or imports a SQLite driver.

The RGAP repository contracts remain in `@rgap/core` because they are part of
the core command and handle model.

## SQLite store

`@rgap/store-sqlite` exports `SqliteRgapStore`. It accepts a file path or
`:memory:`, an optional initial state, and a runtime registry.

`src/schema.ts` declares normalized tables, and Drizzle Kit generates the DDL.
The constructor applies that DDL when it opens a database.

Each command runs in one `better-sqlite3` transaction. The adapter loads the
command's working set, applies the relevant pure core rule, writes only the
rows changed by that command, and appends its audit event. A rejected rule
writes nothing. Records returned to the caller reflect the rows committed by
the transaction.

The working set and write plan are specific to each command:

| Command | Records loaded | Rows written |
| --- | --- | --- |
| Create resource path | Starting folder, occupied path prefixes, executable definition, bindings, and candidate IDs. | Insert each missing folder, the leaf, its normalized executable rows when present, and one audit event per inserted resource. |
| Update resource | Resource, siblings, and the destination folder and its ancestry when moving. | Update one resource row and insert one audit event. |
| Delete resource | Resource and its descendant subtree. | Tombstone the subtree and insert one audit event. |
| Create or amend grant | Relevant parent and child grants, their bindings, and resources needed for containment. | Insert or replace the affected grant bindings, revoke uncovered descendant branches, and insert one audit event. |
| Issue or revoke | The affected grant, token, or grant branch. | Insert or update affected rows and insert one audit event. |
| Authorize | Token selected by hash, grant lineage, requested resource ancestry, and path prefixes required by lineage entries. | Insert one audit event. |
| Resolve bearer | Token selected by hash and its grant lineage. | None. |
| Record invocation | No repository snapshot. | Insert one audit event. |

Parent and child traversal uses ordinary key and parent/child lookups in
bounded batches; the persistence contract does not require recursive SQL.
Every multi-query load observes the transaction's consistent database state.
Bearer resolution is an internal guard operation that validates the token and
its grant lineage without materializing a resource-permission map. `reset` and
initial-state installation are explicit bulk operations and may replace all
rows. Ordinary commands never use those bulk paths.

Rows are inserted parents before children so foreign keys hold after every
statement. Issued bearer values are returned once; token rows contain hashes.

The domain model embeds an executable definition in its resource. The
normalized schema stores the definition in one `executables` row, keyed by
`resource_id`, and one ordered `executable_bindings` row per sealed top-level
input field. Each binding stores the target resource ID and the grant lineage
that authorized `bind`, or administrative provenance. Resource create verifies
that every resource is live and the runtime is registered, then atomically
writes the resource, executable rows, bindings, and audit event. Executable
rows are written only by that create and removed only when their resource is
deleted, so no command updates them and there is no independent executable
tombstone or revision table.

| Table | Contents |
| --- | --- |
| `resources` | Stable resource records and tombstones. |
| `grants` | Grant identity, ancestry, expiration, and revocation. |
| `grant_bindings` | Ordered resource-ID targets for each grant. |
| `grant_binding_permissions` | Normalized permission sets for grant bindings. |
| `tokens` | Token metadata and bearer hashes. |
| `executables` | The normalized runtime and sealed input of each executable resource. |
| `executable_bindings` | Resource IDs and authority lineages sealed into top-level input fields. |
| `audit` | Ordered authorization, mutation, and invocation events. |

## Invocation lifecycle

The token plane authorizes `invoke` on the executable resource. The
orchestrator then:

1. Resolves the resource's executable definition and registered runtime.
2. Revalidates every bound target and its recorded `bind` lineage.
3. Rejects caller values for sealed fields, constructs input without prototype
   inheritance, inserts the bound resource ID strings, and parses the complete
   input when `inputSchema` is not null.
4. Calls the runtime with typed input, an `AbortSignal`, and nested invocation
   methods that accept arbitrary resource IDs.
5. Authorizes each nested ID through the initiating caller or a valid direct
   edge on the current frame. A nested target begins a new frame with its own
   independently revalidated edges.
6. Resolves each nested target's current executable, rejects active-stack
   cycles, and enforces a maximum depth of 32 frames.
7. Normalizes a single value, promise, async iterable, or `undefined`.
8. Parses every output when `outputSchema` is not null, emits `data`, and emits
   `done` automatically.
9. Records redacted facts as `done`, `error`, or `cancelled` in a `finally`
   block.

The audit detail contains resource ID, runtime, grant-lineage IDs, parent
invocation ID, binding resource IDs, timing, and result. It excludes input,
output, and external secret values. Caller cancellation and early iterator
return abort the complete nested call chain.

One root invocation memoizes repeated authorization decisions only for the
authorization-state snapshot that produced them. A nested frame reads
authorization state again before it starts, so revocation affects subsequent
calls without interrupting work already running in a frame.

## HTTP server

`@rgap/server` exposes `RgapCommands` with Hono and
`@hono/zod-openapi`. Each route declaration defines runtime validation and the
OpenAPI contract.

The package generates:

- An OpenAPI 3.1 document.
- An interactive Swagger UI.
- A fetch-based TypeScript SDK with HeyAPI.
- Hono RPC types from the same chained route definitions.

`HttpRgapStore` implements `RgapStore` over that generated SDK and reconstructs
the same repository handles used by the local store.

Resource and invocation operations map one-to-one:

```text
POST   /resources                     { name, executable? }
PATCH  /resources/{id}                { name?, parentId? }
DELETE /resources/{id}
POST   /resources/{id}/invoke         { input }
```

Invoke responds as `application/x-ndjson`, with one serialized `data` or
`done` event per line. Runtime failures fail the response stream. The server
obtains the first event before committing the response, propagates request
cancellation, and closes the runtime iterator when the client disconnects.
`HttpRgapStore` uses generated methods for JSON operations and a streaming
fetch reader for invocation.

## MCP proxy package

`@rgap/mcp-proxy` provides MCP connections, OAuth persistence, an RGAP invoke
runtime, and a mountable Hono app. It accepts deployment-owned credential and
OAuth flow stores rather than choosing secret persistence.

Runtime and app creation are separate because a deployment registers the MCP
runtime while constructing its RGAP store:

```ts
const mcp = createMcpProxyRuntime({
  publicBaseUrl,
  credentialStore,
  flowStore,
});
const store = new SqliteRgapStore({
  url,
  runtimes: { mcp: mcp.runtime },
});
const proxy = createMcpProxyApp({ mcp, store });
```

The app contains one stateless MCP Streamable HTTP route and the public OAuth
callback and client metadata routes, relative to its mount point:

```text
POST /mcp/:connectionId
GET  /oauth/callback
GET  /oauth/client-metadata.json
```

It does not expose the RGAP API. Each MCP request uses its bearer to open the
guarded RGAP repository and invoke `connectionId`. The route handles MCP
initialization locally, forwards request-response methods, advertises no
server-initiated capabilities, and does not provide SSE.

The runtime also exposes `mcp.servers(repository)` for server registration
CRUD. The supplied repository determines management authority. A registration
owns one server resource, one credential resource, and one immutable executable
connection. Replacing its URL replaces the executable connection. Deletion
also removes its associated secret, so an outstanding callback cannot complete.

The package has no listener, environment parsing, database paths, or signal
handling. A parent Hono app mounts it at any path. `publicBaseUrl` identifies
the app's externally visible mount point so callback URLs remain correct when
the route has a prefix.

The proxy depends on `SecretStore` from `@rgap/secret-store` and
`OAuthFlowStore` from `@rgap/oauth-store`. The example injects
`SqliteSecretStore` from `@rgap/secret-store-sqlite` and
`SqliteOAuthFlowStore` from `@rgap/oauth-store-sqlite`. SQLite secret values
are plaintext and remain local example infrastructure.

## Documentation application

`@rgap/docs` is a Next.js application using Fumadocs and MDX. Content metadata
defines navigation order and sidebar groups. The application generates search,
tables of contents, syntax highlighting, theme controls, social images, and
LLM-readable Markdown routes from the same pages. `pnpm docs:dev` serves it on
port 3001 so the HTTP API can run beside it on port 3000.

## Scratchpad

`@rgap/examples` consumes `@rgap/store-sqlite` and `@rgap/core` like an
external TypeScript application. The secret-store app configures one trusted
runtime whose sealed input contains an externally stored credential resource
ID and another runtime that invokes it by resource ID. It creates the outer
executable through an ordinary delegated repository plane without granting
that plane authority over the credential.

Change only store construction to run the same walkthrough against HTTP:

```ts
const store = new HttpRgapStore({
  baseUrl: 'http://localhost:3000',
  adminToken: process.env.RGAP_ADMIN_TOKEN ?? 'test',
});
```

## Property-based invariant suite

`tests/invariants` is a separate workspace package for security properties
that span individual modules. It uses generated resource trees, grant
lineages, requests, and command sequences. A failure reports the random seed
and the smallest counterexample so the sequence can be replayed as an
ordinary regression test.

The suite verifies these properties over the authority dimensions represented
by the protocol:

- ID-based grant-binding containment is reflexive and transitive.
- Every concrete request authorized by a covered child binding is authorized by
  its parent binding.
- Every request allowed through a child grant is allowed through every active
  ancestor in the current resource tree.
- Delegation and token issuance leave the parent's authority unchanged.
- A child grant never outlives its parent.
- Grant amendment revokes children that the replacement no longer covers.
- Grant revocation disables every descendant, while token revocation disables
  only that bearer.
- Resource moves, deletion, and expiration cannot bypass complete-lineage
  evaluation.
- A denied transition does not mutate authorization state.

State-machine checks apply generated commands one at a time and validate the
invariants after every transition. Resource topology changes are evaluated
against current state: moving a resource beneath a bound resource can
intentionally change the covered subtree, but an allowed request must still be
covered by every ancestor. Generated states use the same `GrantBinding`
contract as the core rules: each binding contains one stable resource `id` and
a permission set. The checks use `bindingAuthorizes` for concrete requests and
`setBindings` for grant amendments.

The package also exports a deterministic adapter smoke harness. An adapter
runs one fixed delegation and revocation scenario, then compares normalized
resource paths, grant paths, and authorization decisions with the expected
contract. Generated state-machine checks remain focused on the pure rules, and
adapter-specific integration tests remain beside their adapters.

`examples/invariants.ts` is the deterministic, executable introduction to the
same contract. It checks child-to-parent authorization containment and
cascading ancestor revocation without random generation.

## Verification

`pnpm build` type-checks every workspace package and produces the documentation
site. `pnpm test` runs the core, SQLite, server, and property-based invariant
suites. Core's 100% coverage threshold is a gate over its source rather than a
report, and each downstream package exercises its real adapter instead of a
stand-in.

Continuous integration installs the frozen lockfile and runs three explicit
checks:

```bash
pnpm build
pnpm test
pnpm --filter @rgap/examples invariants
```

The final check executes the deterministic invariant walkthrough against the
SQLite adapter in addition to the property-based invariant package included by
the workspace test command.
